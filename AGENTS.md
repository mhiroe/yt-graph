## yt-graph project

Entrypoint for a workflow v4 project bootstrapped from `docs/spec_provision.md`.

## Basic policy

- `AGENTS.md` carries only repo-specific deltas; the vendored `planner` / `doit` / `done` skills are the canonical task workflow.
- For repo-specific workflow details, see `docs/spec_repo_workflow.md`.
- For product purpose, scope, I/O, and constraints, see `docs/spec_product.md`.

## Starting work

- Read the `docs/spec_*.md` index first, then open only the target section.
- Open only the law `###` sections whose scope overlaps the task; never read law files in full.
- Before implementing, briefly write down the current state, conflict points, and the approach to take.

## task / spec operations

- Markdown documents under `docs/` are the canonical document source. The vendored Core under `.agents/workflow-v4/` projects them into a device-local SQLite DB (`.workflow.nosync/workflow.sqlite`); the repository identity lives in the tracked `.workflow/repository.json`. Never hand-edit either.
- Skills reach the Core only through `.agents/workflow-v4/wf4.sh` (`skill.phase` / `wish.complete` request kinds). If `.workflow/repository.json` is missing, provision once with `.agents/workflow-v4/wf4.sh provision <repository-id>`.
- `planner` clarifies and decomposes a wish's document and presents the readiness decision to the user; `doit` executes one task only after the user's readiness decision; `done` completes the task with recorded verification.
- `done` never closes a wish; wish closure is an explicit user instruction.
- Work-units live in iteration layout: `<component>/<it>/{docs,spec,app}` with
  `active/<label>` links and an optional `current` default. New components are
  opened through the Core (`iteration.open` + `iteration.switch`) — never by
  hand. See `docs/spec_repo_workflow.md` "directory layout".
- Durable repo-only decisions live in `docs/rule_yt-graph.md`; shared laws and the constitution are read from the session entrypoint.
- On spec updates, read index-first and open only the needed sections.

## repo-specific rules

- The primary language is `TypeScript`; the main framework / app shape is `React + Three.js (3D graph) + Vite` web UI over a local API (SQLite).
- External integrations stay behind swappable adapters: YouTube Data API + OAuth, chappy-cli (ChatGPT consult), jev (judgment filter), yt-client / ContentHub (playback). Do not hard-code a specific model or provider in the engine boundary.
- `pnpm` is the canonical runtime / package manager.
- While formal tests are thin, treat a smoke check as the minimal test scope; start with a connectivity check like `pnpm exec node path/to/script.js --help`.
- DDD is not adopted for now; create or grow `docs/spec_domain.md` when domain separation becomes necessary.
- `git-worktree` is not opted in for now; the branch lifecycle assumes normal checkouts.
- Keep overview, usage, environment settings, and setup in README; update it in the same diff when related changes land.
- For lint / test / branch / directory-layout rules, see `docs/spec_repo_workflow.md`.

## Finishing work

- Close tasks via `done`: record the verification and promote durable decisions into `docs/rule_yt-graph.md` or the owning spec.
